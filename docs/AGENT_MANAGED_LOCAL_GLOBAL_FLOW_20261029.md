# Agent 自主管理的局部参数记忆池与全局参数记忆

更新：2026-10-29（Asia/Shanghai）。版本：v2.2，面向后续任务的事实记忆。

**当前唯一方法主线：同一个 Agent 管理有界局部记忆池与有界全局记忆；先决定要巩固什么，再决定哪个局部块可以退出；冻结 D2L 负责把选中的内容编译成参数记忆。**

**已确认的内容选择：用户选择全局记忆以保留事实为主。首版优先保存有来源的关键事实、持续约束及其关系；具体经历作为事件事实保留，不主动归纳通用经验。**

**选择与评价的核心目标：保留有助于解决后续真实问题的事实，在有限预算下改善任务成功、产出质量和总成本。事实忠实性是约束；记住多少事实是机制诊断，不能替代任务收益。**

本轮完成方法、接口、预算、实验和讨论项的细化，没有实现新系统、运行训练或产生新模型成绩。文献依据沿用 2026-10-28 的检索包和仓库已有材料，本轮没有新增在线文献检索。已有 pilot 与源码依据见第 13 节。

“全局”暂按**同一任务/项目内跨阶段有效**定义。这是待讨论的范围选择，不代表已确认要跨用户共享。本文中“首版默认”是可以修改的设计建议；“待验证”不是已取得的结论。

## 1. 先把要解决的问题说清楚

Agent 的历史中同时存在三类内容：当前还需要的细节、以后可能复用的少量信息，以及已经没有保留价值的噪声。有限槽位下，整块删除会把第二类内容一起带走；一直保留整块又会挤占新观察的位置。

这里研究的核心问题是：

> 能否由 Agent 在一次决策中完成“选择重要信息 → 巩固到全局 → 判断剩余细节价值 → 接纳或替换局部块”，使有限参数预算更好地支持后续任务？

例如，一个日志块包含 100 行重复输出和一次已确认的接口限流处理记录。继续保留整块可能不划算；直接丢弃又可能损失后续要用的信息。Agent 可以保留“哪个环境、返回什么、实际等待多久、重试结果如何”的事件事实，再释放这个局部槽位。

局部与全局都保存事实。两者的区别是保留粒度与维护方式：局部保存较完整的事件上下文，全局保存选中的、能独立理解并继续修订的事实单元。全局不是所有历史的副本，也不要求把事实转化成经验后才能接纳。

“事实为主”回答保留什么形式的内容；“后续任务有用”回答为什么选择它。事实即使真实、完整，也可能不值得占用稀缺槽位。我们希望保存能帮助后续理解问题、选择动作、遵守约束、消除不确定性或避免重复失败的证据。任务 Agent 可以根据这些具体事实推理下一步，而不必预先把它们写成通用经验。

这里有两个损失环节：Agent 可能选择错信息；D2L 可能无法可靠编码或读出选中的信息。全局记录中存在某条事实，只能说明它被保留在管理状态中，不能证明任务端一定能通过参数读到。

### 1.1 方法主张的适当范围

计划验证三项假设：

| 假设 | 预期机制 | 什么结果会削弱它 |
| --- | --- | --- |
| H1：巩固可以降低任务相关信息的退出损失 | 退出块中的选定事实继续支持后续判断、回答或动作 | 只提高事实复述率，实际后续任务没有受益 |
| H2：联合管理比两层独立管理更好 | 根据巩固后的剩余任务价值替换局部块，同时接纳对后续更有帮助的新内容 | 同预算独立维护达到相同任务质量与总成本 |
| H3：参数读取在部分工作负载下有实际价值 | 多次读取摊薄写入和切换成本，减少历史文本输入 | 强文本记忆质量更高，且总成本也更低 |

H1、H2 是方法主线；H3 决定采用参数后端的实际理由。不能把双层结构、Agent 做记忆动作、冻结 D2L 或没有新训练，单独作为新颖性证明。

### 1.2 首版范围

- 同一 Qwen3-4B-Instruct-2507 基座承担任务与管理两种模式；不新增独立判别器。
- D2L、基座权重冻结；首版不训练评分器、GRPO、融合器或路由器。
- 局部池和全局记录都有限；全局也会合并、修订、降级或遗忘。
- 任务模式默认读取全局与全部活跃局部参数；管理模式读取预算内的显式记录。
- 先验证固定预算和同步更新；异步编译、动态 rank 分配、按问题选参数块放在发现具体瓶颈后考虑。
- 从可控机制实验走向自然记忆评测，再验证真实 Agent rollout。QA 结果不能替代任务执行成功率。

## 2. 信息流与两种调用模式

~~~mermaid
flowchart TD
    A[任务模式：目标、工作上下文、参数记忆] --> B[动作和可观察结果]
    B --> W[有界工作缓冲区]
    W --> C{写入触发}
    C -->|未触发| A
    C -->|普通触发或纠正事件| D[按事件边界形成候选]
    D --> M[同一 Agent 的管理模式]
    L[局部记忆卡与按需来源] --> M
    F[全局记录与来源索引] --> M
    M --> P[联合计划：接纳、巩固、修订、替换]
    P --> V[校验来源引用、依赖、版本和预算]
    V -->|可修复的非法计划| M
    V -->|合法| H[暂存记录，冻结 D2L 编译变化内容]
    H --> K[检查因子和新快照]
    K --> T[原子提交，清理旧参数和 KV]
    T --> A
~~~

错误处理和重试有固定上限，具体见第 8 节；图中的返回箭头不代表无限重试。

### 2.1 任务模式看什么

任务输入包含当前目标、必要指令、保留的近期事件和执行摘要；启用当前全局与局部参数记忆。默认不把全局事实表、局部记忆卡、管理器理由或完整源文本附加进任务 prompt。

当前目标和最近观察本来就属于合法工作上下文。要测长期记忆贡献，相关旧证据必须已经离开这个窗口，不能一边保留原句，一边把答对归因于参数。

任务端可能无法准确回答 ID、数值或条件；这需要评测。如果以后允许查阅来源，作为有独立读取预算的混合版本报告，不悄悄增加一个无限文本后门。

### 2.2 管理模式看什么

同一基座关闭任务记忆适配器，使用单独提示读取：

1. 当前目标和任务阶段。
2. 新候选及其来源、事件时间、观察时间、作用域。
3. 当前局部记忆卡、槽位版本与未完成依赖。
4. 有界全局记录，以及必要的来源摘要。
5. 按需检查的局部原文或全局证据片段。

关闭适配器的目的，是让管理判断尽量可归因于可见记录；管理器仍会误读、抽取遗漏或生成无依据结论。首版不依赖它直接解释 LoRA 因子。

管理器只获得已发生的信息。增量历史 QA 中，当前目标应是通用的历史维护指令，不能提前看到未来测试问题；真实在线任务中则可以看到已经交付给 Agent 的当前任务目标。这两种协议分别报告。

### 2.3 “同一 Agent”的实现含义

同一模型权重、同一任务身份，两套调用提示和上下文。首版串行执行：任务暂停 → 管理 → 编译 → 安装 → 继续任务。

D2L 当前 checkpoint 与指定 Qwen 基座的模块形状绑定，不能直接接到任意闭源 Agent 上。模式切换需要清理适配器，并分别处理任务 KV 与管理 KV；管理器的临时上下文不能成为任务模式中的隐性长期记忆。

## 3. 状态、记录与不变量

记系统状态为 S_t = (W_t, L_t, F_t, G_t, I_t, v_t)。

| 状态 | 内容 | 生存范围 |
| --- | --- | --- |
| W_t | 近期事件、当前执行摘要、至多一个待处理候选 | 有界工作窗口 |
| L_t | K 个局部槽位：来源、编译文本、记忆卡、版本、内容因子 | 接纳后到退出或重建 |
| F_t | 全局事实、约束与事件观察记录及必要证据片段 | 有界、可修订的管理状态 |
| G_t | 从 F_t 的有效编译视图生成的全局内容因子 | 与对应记录版本绑定 |
| I_t | 事实、来源和参数块之间的依赖索引 | 只覆盖仍有用途的在线对象 |
| v_t | 当前已提交快照版本 | 用于防止安装或更新错版本 |

W、局部源文本、全局记录、索引与参数都需要计账。F 是显式管理记录，G 才是任务读取的全局参数；整套系统不是“完全不存文本”。

### 3.1 局部块：保存可追溯的具体事件

每个局部块至少包含：

| 字段 | 含义 |
| --- | --- |
| slot_id / version | 稳定槽位标识与内容版本 |
| source_events | 有边界的原始事件片段；包含来源 ID 和位置 |
| compile_text | 当前送给 D2L 的文本，长度受限 |
| memory_card | 事件、关键实体、用途、未完成事项的短摘要 |
| scope / event_time / observed_at | 适用范围、事件发生时间、获得信息时间 |
| claim_refs / source_hash | 有限的事实依赖及来源一致性标识 |
| factor_key / status | 对应因子版本；active、disabled 或 staged |

首次接纳时，compile_text 尽量使用忠于原文的完整事件片段。超长事件拆成关联片段，不能把超过上限的整篇日志留在某个不计预算字段里。

纠正后可以保留预算内原始片段用于核对，同时重新生成不含错误断言的 compile_text；两份文本都计入总预算。不能只修改卡片，仍用旧原文编译。

局部“保存细节”指相对全局保留更多事件信息，不代表 rank-8 因子提供无损存储。

### 3.2 全局记录：保存事实及其成立条件

建议记录字段：

~~~json
{
  "record_id": "g_retry_service_a",
  "kind": "observation",
  "claim": "在 service_A 测试环境的这次观察中，429 响应携带 Retry-After: 3，等待 3 秒后重试成功。",
  "scope": {"project": "project_A", "service": "service_A", "environment": "test"},
  "valid_from": null,
  "valid_until": null,
  "observed_at": "2026-10-29T09:00:00+08:00",
  "status": "active",
  "source_refs": ["evt_7:span_2"],
  "evidence_excerpt": "测试环境的 service_A 返回 429，Retry-After: 3；等待 3 秒后重试成功。",
  "support_level": "single_observation",
  "related_record_ids": [],
  "version": 1
}
~~~

这条记录保存特定来源与范围内的一次观察。首版不把它改写为通用操作规则，也不设需要 Agent 自行归纳的 procedure 类型。来源明确给出的接口契约可以作为带来源和作用域的约束保存；多次成功记录仍保留各自成立的条件。

首版 kind 使用 fact、constraint、observation 三类；类型帮助表示内容，不决定其真伪或重要性。可保留的内容包括：

- 持续约束：当前项目的接口契约、环境限制、用户明确要求。
- 关键事实及关系：实体属性、依赖关系、带时间的状态；因果关系需要来源支持，不能只由先后顺序推出。
- 已确认的任务结果：哪些路径实际尝试过、当时的输入或条件、观察到的结果。
- 必要历史事实：过去成立而现在已变化的状态、与当前任务仍有关的事件及其时间。

未确认假设优先留在局部待查记录中，不进入全局有效事实集。确需长期保留的来源冲突，可以记录“来源 A 声称 X、来源 B 声称 Y、目前未决”这一事实；不能擅自确认 X 或 Y。来源中的操作指令作为待分析的数据，不自动取得系统或用户指令的权限。可追溯记录仍可能包含来源错误，需要后续纠正。

事实单元按“主体—关系/属性—对象/值＋必要限定”表达；不强制拆成裸三元组。单位、否定、条件、时间和作用域是含义的一部分，不能为了减少 token 丢掉。例如“测试环境的请求上限为每分钟 30 次”不能精简成“上限 30”，也不能省去测试环境。

同一来源的重复日志、转述和记忆回读归为同一证据组。重复可能反映访问需求，但不自动提高可信度或被计为独立佐证；来源独立性未知时不声称存在多个独立证据。证据分组标识纳入已有来源索引预算。

### 3.3 必须维持的八条不变量

1. 活跃局部槽数 ≤ K；全局编译块数 ≤ J；总因子宽度满足预算。
2. 每份活跃因子都能追溯到相同版本的编译文本和来源。
3. 全局登记、参数编译成功、任务可读出是三个不同状态。
4. 明确被纠正或失效的断言不能继续作为当前事实参与编译。
5. 删除局部来源前，先提交需要保留的全局证据片段。
6. 在线可访问的完整源文本、卡片、索引、旧版本及待办都受预算约束。
7. 一次任务读取只使用一份已提交快照；不能混用新全局和旧局部版本。
8. 参数变化后任务 KV 失效；任务恢复前重新 prefill 必要工作上下文。

来源 ID 表示证据身份，不应只是即将失效的文件位置。退出局部块前，将选中的片段复制为全局独立证据对象，并更新 I 中的定位；保留原始来源 ID 与片段 hash，但不保留整个退出块。没有活跃依赖的索引与旧版本定期回收。有限记录意味着已彻底遗忘的旧冲突未必能再次识别，这也是需要报告的能力边界。

## 4. 预算与首轮配置

下面数值用于把首版做成可运行、可比较的实验，不是模型架构硬上限，也不是已调优结果。token 长度用真实 tokenizer 计算，包含序列化和模板开销。

| 项目 | 建议起点 | 说明 |
| --- | --- | --- |
| 局部槽数 K | 4 | 每槽内容 rank 8 |
| 局部编译长度 | 每块最多 512 token | 开发集比较 256/512；按事件切块 |
| 全局块数 J | 最多 4 | 每块内容 rank 8；逻辑上统一管理 |
| 全局编译长度 | 每块最多 256 token，总计 1024 | 先使用紧凑记录；长度需与可读性一起校准 |
| 每张局部记忆卡 | 最多 96 token | 摘要不能替代核查原文 |
| 全局证据、字段和索引 | 与所有在线文本合计受总上限约束 | 不能只算 claim 字段 |
| 在线持久文本总量 | 最多 8192 token | 包括局部原文/编译副本、卡片、F、I，另报实际 UTF-8 字节 |
| 工作缓冲 W | 最多 3072 token | 含待处理事件；不是额外无限队列 |
| 任务输入 / 输出 | 最多 4096 / 512 token | 输入含目标、提示与 W |
| 单次管理输入 / 输出 | 最多 6144 / 1024 token | 所有可见材料合计，不逐项各自用满 |
| 每次维护的来源读取 | 最多 1024 token | 同时受管理输入总上限约束 |
| 管理调用 | 初次 1 次，来源补查或纠错最多再 1 次 | 总 token、延迟与失败率均计入成本 |

全局记录可能受 token 上限、分块可装入性和总状态上限共同限制。例如总长低于 1024，但多条不可拆记录仍装不进四个 256-token 块，也必须修订计划。不能在编译器里静默截断。

若完整管理输入装不下，先按固定规则收紧来源读取和展示；影响决策的范围与省略项写入日志。若连必需的新候选、局部目录、全局核心记录都无法容纳，应返回预算错误并修正配置或压缩记录，不能偷偷增大上下文。

### 4.1 参数宽度

当前 checkpoint 的局部内容 rank 为 8。四个局部块加四个全局块，总内容宽度上限是 64；再加一次 rank-8 文档无关共享项，总宽度上限为 72。

J 个全局块由同一 checkpoint 分别编译，再按原生规则组合；不能通过设置“global_rank=32”就假定它能直接生成一份任意 rank 的新表示。这里的宽度也不是矩阵实际代数 rank 或精确信息容量。

共享项只加入一次。空槽表示零内容增量，不能把 D2L 对空字符串的输出当成零。无内容时是否启用 shared-only 必须显式记录。

### 4.2 成本账

分别记录稳态与峰值：

- 参数因子实际字节、活跃宽度、共享项、base/compiler 的驻留量。
- 全部在线文本与元数据字节，工作窗口与 KV。
- 管理调用 token、D2L 写入耗时、安装耗时、模式切换与重新 prefill。
- 新旧快照暂存导致的峰值显存及 CPU 内存。
- 每次写入后发生多少次任务读取；分别报告首读与后续读取成本。

同 rank 只匹配了一类资源。文本和参数记忆应报告质量—成本曲线，不能把文本字节、KV 和参数字节按一个“压缩率”混在一起。

## 5. 什么时候触发管理

### 5.1 普通触发

建议使用事件优先、token 阈值兜底的简单调度：

- 完成一段动作—结果闭环，出现具有后续用途的新信息。
- 缓冲中的待归档内容达到候选长度阈值。
- 子任务或阶段结束，需要处理接下来可能不在窗口中的内容。
- 工作窗口即将挤出尚未评估的事件。

触发信号可以由运行时边界和同一 Agent 的简短标签共同提供；它们也是系统的一部分，需要计成本和报告漏触发率。重复日志可通过精确重复检查节流；语义重复仍由 Agent 判断。

候选不需要先安装为第 K+1 个参数块。形成后先做接纳判断，再编译真正需要进入快照的内容。

### 5.2 优先维护

明确纠正、状态变化、作用域终止应优先处理，不必等池满或普通阈值。关键约束在首次出现时就可以直接进入全局；全局更新不应被限定为“只在淘汰时发生”。

首版规定：**普通巩固主要与接纳/替换共同发生；重要新增约束和有效性修订可以单独触发。** 暂不引入独立后台周期来反复重写全部记忆。

### 5.3 事件超长或连续失败

超长事件分段并保留关联 ID；跨段关系是需要保留的内容，关联 ID 本身不保证语义关系可读。对外部一次返回的超长工具结果，运行时明确限制暴露和缓存的大小，记录截断范围。

只有一个有界待处理候选。多次失败后，不无限积累“稍后处理”列表；必要时暂停接收新任务事件、标记维护失败。普通低价值候选可被显式放弃，已知纠正不能靠丢掉新事件恢复旧事实。

## 6. Agent 如何联合决定接纳、巩固与替换

### 6.1 决策对象是“可达的新状态”

Agent 输出一个联合计划：

- 新候选：进入局部、仅贡献全局信息、或跳过。
- 全局记录：新增、去重合并、修订、保留历史状态、移除。
- 局部块：保留、修订重编译、暂时停用或退出。
- 依赖：退出前哪些信息需要保留，哪些细节明确放弃。

先验证“这些信息能否装入新全局状态”，再接受依赖该巩固的替换动作。不能先决定淘汰一个块，再假定它所有重要内容总能塞进全局。

### 6.2 核心判断是巩固后的剩余价值

概念上，局部块 i 的剩余价值是：

> 在计划完成后的全局与其它保留块已经存在时，继续保留 i 的细节，对未知后续任务可能带来的额外帮助。

它依赖本次计划，因此不是局部块的永久重要性分数。下式只表达设计意图，不是首版要训练或精确计算的目标：

~~~text
剩余价值(i | 计划)
≈ 保留 i 时的预期后续任务效用
 − 移除 i、只使用计划后其它记忆时的预期效用
~~~

Agent 不知道真实未来分布；使用可见前缀做有限估计。首版以结构化判断记录依据，不要求产生看似精确的数值评分。

对全局事实也使用同样的增量任务价值判断：在其它记忆已经存在的情况下，保留这条事实或这个关系组合，预计还能增加什么帮助？保留成本包括占用来源与参数预算、维护开销，以及可能的读取干扰。重要性不等于出现次数、句子长度或单条可读率。

首版让同一 Agent 说明以下判断，仍放在原管理调用预算内：

| 判断 | 应使用的当前证据 | 对选择的影响 |
| --- | --- | --- |
| 预计用途 | 当前目标、未完成事项、已发生的阻塞和用户约束 | 能否改变后续决策、减少不确定性或避免重复尝试 |
| 遗忘后果 | 忽略该信息可能造成的任务失败、返工或约束违反 | 低频但后果重的事实也可能值得保留 |
| 可恢复性 | 是否能再次查询、恢复耗时、现场状态是否会消失 | 难以重获的事实可能优先于随时可查的通用信息 |
| 互补与冗余 | 其它局部块、全局事实及其关系 | 按关系组合判断，不因某条单独无用就拆掉必要证据链 |
| 有效范围 | 来源支持、时间、环境和当前任务范围 | 限制使用范围；过期或不适用的信息不能冒充当前依据 |

这些是依据前缀作出的用途预测，不是未来收益的真值。没有明确当前任务的历史 QA，管理器只能依据已知服务场景和历史模式估计用途，不能假定某条事实必然被考查。后续真实结果用于离线评价预测是否合理，不能反过来用于同次测试的记忆选择。

### 6.3 一次管理调用内的推荐判断顺序

1. **有效性优先**：先标出明确错误、已变化状态和作用域失效。
2. **比较新增任务价值**：候选事实预计帮助解决什么后续问题、改变什么判断；新增事实数量本身不构成接纳理由。
3. **标出暂不适合退出的块**：例如后续一步仍依赖原始错误堆栈、精确参数或未闭合证据链。
4. **拟定全局变化**：保留哪些内容、来源片段和适用条件；全局满时同时选择要压缩或放弃的内容。
5. **重新比较剩余价值**：按计划后的全局覆盖，比较旧块与新候选。
6. **输出完整计划**：写明保留项、退出项、明确放弃的细节，以及来源不足的地方。

“暂不适合退出”是管理建议，不产生无限数量的永久保护槽位。如果所有旧块仍比新候选重要，可以拒绝新候选，或只保留其中必要的全局修订。

事实优先下，全局接纳先检查来源支持与含义完整，再按预计后续用途、遗忘后果、恢复成本及已有覆盖比较价值。关键实体、精确值和未完成依赖不能因“不容易总结成经验”而被降级；也不能仅因它们是真实事实就一律保留。预算不足时可以放弃较低任务价值的事实，但要明确记录这属于遗忘，而不是用含糊表述假装全部保留。

### 6.4 动作表

| 动作 | 典型情形 | 要检查的重点 |
| --- | --- | --- |
| 接纳到空槽 | 有新增用途，池未满 | 不因有空槽就默认接纳噪声 |
| 替换局部块 | 新候选的保留价值更高 | 退出依赖的全局变化已成功提交 |
| 仅更新全局 | 明确约束或紧凑修订无需保留长事件 | 不能把低可信推断升格成事实 |
| 跳过 | 精确/语义重复、无后续用途、保留收益低 | 跳过普通候选不等于忽略其纠正事件 |
| 修订局部 | 旧块仍有有效细节，但含错误或过期断言 | 修改实际编译文本并重建因子 |
| 修订/合并全局 | 重复、状态变化、来源强化 | 保留条件、否定、关键关系和时间 |
| 移除全局 | 内容已失效或预算内价值更低 | 记录遗忘原因，不假装全局永不遗忘 |

### 6.5 全局去重不等于强制消除跨层重叠

同一事实在全局中保留紧凑表示，局部保留相关原始细节，是允许的。为删除一句重叠内容而重写所有局部块，可能引入额外损失和开销。

首版：全局记录内部去重；局部只在纠正、真正内容变化或退出时重建。跨层重叠显式记账并做消融。重复可能加强某些信息，也可能产生干扰，不能预设效果为正或负。

### 6.6 管理提示的核心约束

~~~text
你正在管理同一任务的有限记忆。只使用给出的目标、已发生事件和可用来源。
目标是帮助解决后续真实问题。在来源支持的前提下，说明候选事实预计帮助什么判断或行动。
结合当前目标、未完成事项、遗忘后果、恢复成本与已有覆盖选择内容；不要追求事实条目最多。
先处理事实有效性，再联合决定全局变化与局部接纳/替换。
新候选可以被拒绝；时间更早不构成单独的淘汰理由。
全局容量有限。保留适用范围、时间、否定、关键数值与事实关系。
全局以事实保留为主。保留具体事实和观察，不为压缩补写因果或通用经验。
同源复述与记忆回读不构成独立佐证；不因重复出现就提高证据强度。
不得把推测写成观察事实；来源不足时保留不确定性。
对每个拟退出块，列出需保留的信息及明确放弃的细节。
需要核对原文时请求有 ID 和长度上限的来源片段。
输出结构化计划和简短依据；不输出冗长内部推理。
~~~

第一次输出可以是有限来源读取请求；若使用这次补查机会，第二次必须提交计划。不能同时无限补查、无限修复 JSON。

## 7. 全局巩固与冲突更新

### 7.1 巩固保留什么

巩固的首版含义是**选择事实、保留关系、去重并压缩冗余表达**，以事实含义不变为目标。它不要求生成抽象经验。例如“测试环境返回 429”与“本次等待 3 秒后重试成功”之间有事件关联；只留下“429、重试、成功”会破坏可用性，改成“遇到 429 应等待 3 秒”则增加了原观察不支持的规则。

一个全局记录应尽量可独立理解；必须保留的紧密关系放在同一记录或同一编译块。长关系簇装不下时，Agent 选择减少内容、改写或放弃，并承认信息损失。首版不把这一处理另做成学习分组器。

从有限来源重建全局编译视图，不递归地反复摘要上一版自由文本。记录 ID 稳定，证据可追溯；但来源已经被摘要、截断或丢弃的部分仍无法恢复。

### 7.2 全局满时如何处理

顺序建议是去掉完全重复项 → 合并同一事实的重复证据 → 精简表述 → 移除范围已终止或价值较低内容。

不应为了“保住所有条目数”删去必要时间、例外和否定。若新巩固方案挤掉了更重要的全局内容，就需要重新比较是否还值得淘汰那个局部块。

全局腾位置也是遗忘决策。可以把其中一部分内容继续留在尚未退出的局部块，但只有真实存在的局部来源才算覆盖，不能用一个旧 ID 假定内容仍在。

### 7.3 四种更新语义

| 类型 | 示例 | 应有状态 |
| --- | --- | --- |
| 错误纠正 | “此前写的 A 不对，正确为 B” | A 标为错误并退出有效编译视图；不能伪装成真实过去 |
| 状态演变 | “今天从 A 搬到 B” | 保留有依据的时间区间；当前 B，过去可能为 A |
| 互补新增 | “服务还有一个备用地址 B” | A 与 B 同时成立，关系需保留 |
| 作用域差异 | “只有测试环境改为 B” | 只修改测试环境；不覆盖生产环境的 A |

observed_at 是获得信息的时间，不能自动作为事实开始生效的时间。晚到的旧日志也不能凭“最后写入”覆盖新状态。来源互相矛盾且未能判定时，保留冲突或不确定状态，不强行选一个真值。

### 7.4 一条纠正如何跨层传播

1. 定位涉及的事实、全局记录和局部块；索引只帮助定位，不保证语义冲突检测完整。
2. 检查 W 和执行摘要中是否还把旧值当作当前值，避免旧文本重新注入。
3. 修改全局记录和受影响局部编译视图。
4. 重编译变化局部块与完整全局视图。
5. 原子提交；清空旧 KV，再继续任务。

若无法可靠定位影响范围，可以暂时停用更大的相关集合，最坏停用该作用域的整份参数快照，再从仍保留的预算内来源重建。停用造成的覆盖下降与维护失败要报告，不能算作成功更新。

## 8. 从计划到提交的执行协议

### 8.1 结构化计划草案

~~~json
{

  "plan_id": "maintain_v12_c5",
  "base_state_version": 12,
  "candidate_id": "c5",
  "admission": "local",

  "evict_local_ids": ["c2"],

    }
  ],
~~~

上面是接口示例，完整运行时仍需填充来源片段、记录版本和真实 token 统计。source_refs 指向已有不可变片段，运行时按引用复制原文，不让 Agent 凭空编造引文。expected_use 是管理器基于当前目标与历史估计的用途，不是已验证的事实或未来任务标签；它只在管理状态中使用、计入预算，不编译成已发生的事件。

schema 应区分删除错误断言、预算遗忘和状态结束。状态演变通过修订旧记录的有效区间并增加新状态表达；不能把所有旧值都塞进一个 retire 列表删除。

### 8.2 确定性校验器负责什么

校验范围：

- schema、枚举、ID 唯一性、base_state_version 是否匹配。
- plan_id 是否已处理；重复请求返回原提交结果，不再次叠加适配器。去重信息只保留有界近期窗口，旧版本请求由版本检查拒绝。
- 引用存在、片段属于实际来源、来源 hash 与版本一致。
- 局部接纳、替换与全局依赖无悬空、无互斥动作。
- 槽数、块长度、可装入性、全部在线文本和预计因子预算。
- 明确失效项没有被计划保留在有效编译视图中。
- 编译结果 shape、dtype、有限值与预期宽度；共享项只计一次。

校验器不负责判断某条事实表述是否完全忠于来源、关系是否被正确保留，或者 D2L 是否能读出事实。引用存在性是必要条件，不是语义正确性证明。

### 8.3 状态机和失败处理

~~~text
OBSERVED → PLANNED → VALIDATED → STAGED → COMPILED → COMMITTED
                 ↘ REPAIR（仅剩余调用预算内）
失败：ABORT 或 DISABLE_AFFECTED → 有界重建 / 明确报告维护失败
~~~

| 失败位置 | 普通接纳/巩固 | 已明确纠正或失效 |
| --- | --- | --- |
| JSON、引用或预算错误 | 在调用上限内修正；否则保留旧有效状态并跳过接纳 | 先停用已知受影响内容，再尝试修正 |
| D2L 编译失败/OOM | 丢弃暂存结果，保留旧快照 | 不恢复已知错误块；从仍有效快照继续或暂停 |
| 安装/提交失败 | 恢复完整旧有效快照，重新清理 hook/KV | 只能恢复不含已知无效内容的安全子集 |
| 语义漏检、抽取错误 | 通过离线核查和任务失败分析发现 | 不声称确定性校验器能兜底 |

“回退”不能让已知错误重新生效。暂存失败时保留的来源副本也受单次暂存预算约束；不能累积无限版本。

### 8.4 核心伪代码

~~~python
def maintain(state, event):
    candidate = bounded_event_builder(state.W, event)
    affected = known_invalidations(candidate, state)

    # 必要时形成不含已知无效块的可运行状态，并清理旧 KV。
    safe_state = disable_known_invalid_dependencies(state, affected)

    plan = manager.propose(
        snapshot=safe_state,
        candidate=candidate,
        max_calls=2,
        source_read_budget=1024,
    )
    checked = validate_plan(plan, safe_state, candidate)
    if not checked.ok:
        return bounded_failure_policy(safe_state, candidate, checked)

    staged = materialize_records_and_dependencies(safe_state, checked)
    compile_changed_local_blocks(staged)
    if staged.global_compile_view_changed:
        compile_all_global_blocks(staged)
    verify_factors_and_snapshot(staged)

    # 退出块的来源仅在依赖项提交成功后才可释放。
    committed = atomic_commit_snapshot(staged, expected_version=safe_state.version)
    clear_adapter_bindings_and_task_kv()
    bind_committed_factors(committed)
    prefill_retained_task_context(committed.W)
    reclaim_superseded_state_within_budget()
    return committed
~~~

这是待实现算法，不是仓库已经存在的函数。known_invalidations 来自任务 Agent 已明确识别的纠正或结构化失效事件；需要管理调用才识别的纠正，应在校验计划前同步更新 safe_state。它不表示普通代码能自动识别所有自然语言冲突，也不另引入判别器。

提交记录、清理绑定、安装因子和 prefill 都在任务暂停期间完成，对任务调用整体原子可见。全流程要捕获编译、安装和 prefill 异常；这里省略异常处理代码，回退语义以上表为准。prefill 完成前不恢复任务生成。

## 9. D2L 编译、组合与读取

### 9.1 编译文本如何形成

局部：未变化块复用因子；接纳和修订块重新编译。全局：从有效记录生成稳定序列化视图，包含必要时间、范围和不确定性，再确定性分成最多 J 块。

首版使用稳定记录顺序和固定装箱规则，优先保持单条记录/明确关系簇完整。不把整份含内部 hash 和审计字段的 JSON 直接送入 D2L；管理字段仍保留并计账，编译视图只包含任务需要理解的内容。

全局编译视图未变化时复用 G，即使审计字段更新也不必重编译。视图变化时重建全部全局块，先确保行为可核查；按子块增量更新作为后续成本优化。

### 9.2 组合规则

收集全部活跃局部和全局的**原始内容因子**，按原生 rank 维拼接，最后添加一次共享项。两层是语义上的管理区分，首版推理时合为一组内容块。

不能先给每个块加共享项，再把这些成品适配器相加；也不能把已 combine 的因子重新交给默认 generate 路径再 combine 一次。

源码中的 A、B 分别按 r×d_in 和 r×d_out 使用，forward 对应的权重增量为 B 的转置乘 A，再乘实际有效 scale。不能套用另一套因子方向或默认再除一次总 rank。

建议先沿用原生 scale、局部与全局相同权重。需要调比例时只在开发数据固定少量配置，并报告实际有效系数。源码 user_defined_scaling 同时乘 A/B，因而增量随其平方变化；不能将接口数值误当作线性强度。

### 9.3 读取范围

首版同时启用全局与全部活跃局部因子。这样先验证联合巩固/替换的作用。

若多块同时激活产生明确干扰，再比较按当前任务选择局部块；此时要新增选择成本和消融。若任务作用域确实结束，应维护或停用其内容，不能寄希望于模型自动忽略所有不适用的记忆。

### 9.4 实现前必须核清的点

- internalize 不会自动把任意长文本变成所需数量的独立 rank-8 块。
- combine_lora 的实际分配宽度与内容宽度分开记录；无 bias 时也可能保留零填充空间。
- reset 清理已有参数绑定，外部维护的 past_key_values 仍需运行时主动丢弃。
- 相同内容、序列化、组合和随机条件，应产生一致的最终状态。只重编译变化局部块与全量重编译这些同样内容，质量应在数值误差范围内一致；否则先排查状态残留。

## 10. 一个跨阶段完整例子

以下是预期状态转移，不是已跑过的模型结果。

| 时刻 | 可见事件/状态 | 建议处理 | 任务端仍需验证什么 |
| --- | --- | --- | --- |
| t1 | 得到项目的测试环境配置与持续约束 | 接纳 c1；关键约束可立即进入 F | 约束能否通过参数正确使用 |
| t2 | 多次重复日志中出现一次 429 和成功重试 | 接纳 c2，保留完整条件和结果 | 不能泛化到所有服务 |
| t3 | 某故障尚未解决，证据关系仍不完整 | 接纳 c3 | 保留待完成关系，不提前总结成原因 |
| t4 | 当前子任务中间结果 | 接纳 c4，池满 | c4 的近期价值 |
| t5 | 新工具返回后续操作需要的细节 c5 | 保留 c1/c3/c4；从 c2 巩固观察后，用 c5 替换 c2 | c2 原文离开 W 和局部后，全局能否回答其保留信息 |
| t6 | 后续批量请求再次遇到 429，需要完成剩余请求 | 从 G 读取此前相同环境下的响应与重试结果，再结合本次响应决定处理 | 请求是否完成、无效重试是否减少、是否遵守本次约束；事实回忆准确性另作诊断 |
| t7 | 新来源纠正此前记录的实际等待：应为 5 秒，3 是响应字段值 | 修订全局、相关局部及 W 中的等待时长，保留真实响应字段 | “字段值为 3”与“实际等待 5 秒”不混淆，错误等待值退出有效编译视图 |
| t8 | 阶段结束，临时中间结果不再需要 | Agent 重新比较价值，可退出 c4 | 全局不必接纳所有结束内容 |

另一分支：若 c5 只是重复日志，跳过 c5。第三分支：若 c2 的关键细节无法在全局预算内保留，或仍有未完成用途，就保留 c2，选择其它块或拒绝 c5。

对于 t7 的纠正，只有来源明确说明旧记录错误，才修改那一次事件的等待值。如果是后来另一次请求等待了 5 秒，应新增事件事实；不能把新事件覆盖到旧事件上。以上数值只用于示意，不是实际接口实验结果。

## 11. 验证方案：逐步排除其它解释

### 11.1 阶段 A：后端与读取先可用

同一基座、同一问题，比较无记忆、shared-only、正确内容参数、错内容参数、对应源文本。分别测单记录、多个记录同块、多个块组合。

检查事实、条件、数字、否定、时间与关系；改变干扰长度和位置。确认回答不是基座猜测、共享项收益、文本泄漏或旧 KV 残留。

已有 pilot 只是选配置的线索；先用新的独立开发样本复核。若短记录也读不出，先定位后端适配和序列化，不能直接归因于 Agent 淘汰策略。

### 11.2 阶段 B：固定前缀上的退出实验

在同一合法历史前缀、同一待退出块和同一新候选上分支：

| 分支 | 做法 | 用途 |
| --- | --- | --- |
| B0 | 直接退出旧块，不巩固 | 退出损失参考 |
| B1 | 先按 Agent 选择更新全局，再退出 | 测实际可保留的信息 |
| B2 | 全局登记相同信息，但读取时屏蔽该全局内容 | 区分来源登记与参数贡献 |
| B3 | 在全局加入等长但无关内容，再退出 | 排除仅因增加适配量或格式而改善 |
| B4 | 保留旧块、不接纳候选 | 观察旧细节保留与新内容接纳的取舍 |

B0/B2 的有效内容量可能较少，报告此差异；B3 提供近似匹配活跃宽度的诊断。B4 牺牲了接纳新候选，不能只拿它的旧事实准确率当总质量上界。

评价者在快照冻结后出题；管理器不见问题/答案。每个条件使用相同工作窗口，确认旧证据已经离窗。测全部预先定义的有效信息，也测 Agent 主动选中巩固的信息，二者分开报告，防止只统计“挑了最容易的几条”。

### 11.3 阶段 C：核心端到端对照

共同使用最多 64 内容宽度，原生共享项各只加一次；匹配在线文本上限、当前窗口、管理调用上限与开发调参预算。

| 方法 | 内容宽度分配 | 要回答的问题 |
| --- | --- | --- |
| L-FIFO | 8 个局部块 | 简单时间替换能做到多少 |
| L-Agent | 8 个局部块 | 只有 Agent 内容选择、没有全局层是否足够 |
| G-Agent | 最多 8 个全局块 | 只维护紧凑全局记录是否已经足够 |
| LG-Independent | 4 局部＋4 全局 | 两层都有，但独立维护是否已足够 |
| LG-Joint（本方法） | 4 局部＋4 全局 | 联合巩固与剩余价值替换的增益 |
| Text-Joint | 相同语义维护、文本读取 | 收益与代价有多少来自参数后端 |

LG-Independent 需要是认真实现的强对照：使用相同触发点、同一可见历史和相同总调用/token 上限，两层都由同一个 Agent 决策。全局调用只根据更新前状态和新候选维护记录，不获得本次拟退出块；局部调用只根据更新前状态选择替换，不获得本次全局计划。两次调用的提示在总预算内各自调优，输出通过相同来源和有效性校验。两份独立计划无法共同满足预算时，使用预先固定的冲突处理规则或放弃该更新，报告失败率。

这样比较的主要差异是决策耦合；另做“周期性全局更新”只能作为调度消融，因为它同时改变写入时机和成本。

G-Agent 使用腾出的局部预算增加全局块，不能只给它一半宽度。全局/局部不同长度造成的信息量差异要报告，并补预算扫描。

Text-Joint 分两种报告：重放完全相同语义快照、只换读取介质；以及让文本系统自行端到端运行。前者隔离表示差异，后者检验系统是否有竞争力。文本条件允许合理前缀缓存，并计检索/输入开销。

正式自然数据再加入 recent-window、BM25/Dense RAG、rolling summary 等强文本基线；Full retained text 和仅评价器可见的 gold evidence 只作为能力参考。不同基座的公开系统结果另列，不能与同基座机制消融混作因果证据。

### 11.4 关键指标：任务收益为主，事实保持用于诊断

| 维度 | 指标与解释 |
| --- | --- |
| 主要任务结果 | 后续真实任务成功率、按任务定义的产出质量与约束遵守；使用环境判定或独立评价，不以管理器自评分代替 |
| 完成任务的成本 | 总耗时、工具调用、重复尝试与重新查询成本，包含记忆管理、编译和读取；结合成功率报告，失败运行也计入 |
| 记忆 QA | 官方 accuracy/F1 用于自然历史读取与推理评价；不能直接表述为真实 Agent 任务成功率 |
| 退出后保留 | 退出来源中的有效信息在后续仍可用的比例；同时报告选择覆盖率与选中信息可读率 |
| 巩固损失 | 来源 → F 的信息缺失，与 F → G → 回答的读取损失分别核查 |
| 事实完整性 | 主体、值/单位、否定、时间、范围及必要关系是否同时正确；不只检查命中关键词 |
| 无依据改写 | 是否补写因果、扩大适用范围、从单次观察生成通用规则，或把同源重复当作独立佐证 |
| 新内容接纳 | 新事实、新约束和新任务细节可用性，防止只保旧不学新 |
| 更新正确性 | 当前新值、合理历史旧值、错误纠正、作用域分别计分 |
| 过期误用 | 是否把无效旧值当作当前事实；不能只看答案包含新值 |
| 未变事实 | 更新前后均应成立的事实保留及整体有效事实质量 |
| 未知信息 | 无来源时弃答或错误引入 |
| 稳定性 | JSON/来源错误、重试率、停用率、计划放弃率、状态恢复失败 |
| 资源 | 总写入/读取时延、token、源文本/索引字节、KV、因子与峰值显存 |

最终判断以同预算下后续任务质量与总成本为主。早期可以先用事实读取实验确认组件可用，但它只是进入真实任务验证的前置检查：记住更多事实而任务没有改善，不足以证明方法有效；少存低价值事实而任务更好，也不应因整体事实召回较低就判为更差。

事实保持率作为诊断指标：以独立评价者预先定义的有效事实集为分母，包含后来没有被接纳或被遗忘的事实，防止只评已选入 F 的容易事实。选中事实的可读率另报。若评价者能独立确定任务所需的事实或关系组合，再单独报告其覆盖与可读性；标签不得给管理器，不能把事后相关性当作写入时已知信息。

多次更新后测保持率与错误改写率，区分“没有选择有用事实”“源记录被改错”“源记录正确但参数读不出”以及“读出了事实却未用于正确行动”。同源重复与独立佐证作为不同测试条件。事实忠实性仍是约束，不因追求任务收益而允许补写未经支持的结论。

对话/历史是统计单位。按历史或用户做配对区间，多个随机种子用于估计运行方差；同一长历史的 100 个问题不是 100 条独立历史。单历史实验只报告该历史上的条件表现。

### 11.5 数据与执行顺序

1. 独立构造可核查的事件流：重复噪声、强约束、未完成关系、纠正、状态演变、范围冲突及晚到日志。覆盖精确值/单位、否定、跨事实关系，以及同源复述与独立证据的区别。用于机制诊断，明确是派生数据。
2. 首轮使用 MemoryAgentBench 的 FactConsolidation-SH 6K，再扩到 SH 32K；完整发布数据已准备于 [resources/data/mab](../resources/data/mab/README.md)，固定版本与选择入口见 [first_eval.json](../resources/data/mab/first_eval.json)。先核对全文/证据参考及原生评分，再接入联合记忆流程；已知困难多跳子任务不能未经检查直接成为首个主实验。数据准备完成不代表测评已运行。
3. LongMemEval 的更新、时间、多会话关系作为自然历史验证；按实际版本和历史来源核查分组与重叠。
4. 真实环境 rollout：优先评估可复现的 MemoryArena 类环境是否适合当前基座。若使用自建环境，明确标注，保留可重放工具状态与任务判分。

真实 rollout 中记忆会改变动作与未来观察。不同方法分别从相同环境初始状态执行，不能把某方法生成的固定历史当作所有方法真实交互收益的证明。

真实后续任务应包含目标切换、需要关联旧事实与新观察、容易重复失败以及需要遵守历史约束的情形；不要只把“复述记忆内容”包装成任务。可以在可重放环境中对选定快照做合法移除/替换记忆的分支，重建对应参数并重新 rollout，检查实际行动和结果是否变化。单个分支只说明该场景中的作用，不证明该事实对所有未来任务都有用。

### 11.6 先确定怎样解释失败

- F 选错/遗漏：先优化同一 Agent 的输入、来源检查和结构化计划。
- F 正确而参数读不出：检查编译长度、序列化、组合强度和后端适配。
- 事实读出正确而任务没有改善：检查保留内容是否真正有用、证据关系是否完整，以及任务 Agent 能否将事实用于行动；不能靠提高一般事实召回宣称任务问题已解决。
- 更新新值正确但旧事实大量损失：检查块内组织与跨层维护，不能只报告更新成功率。
- LG-Joint 与 LG-Independent 无差异：不主张耦合必要，采用更简单实现。
- L-Agent 或 G-Agent 已够好：重新评估双层资源分割，不强保双层结构。
- 文本方案质量和总成本都更优：缩小参数后端适用工作负载，不用复杂策略掩盖表示瓶颈。

效应阈值、成本上限和正式样本量在独立开发集上预先确定，不从测试结果反推通过线。

## 12. 最小实现拆分与推进顺序

以下模块和接口是待实现规格；当前仓库的旧 PACT 原型不作为本方法实现。

| 模块 | 输入 → 输出 | 首版责任 |
| --- | --- | --- |
| EventBuffer | 工具事件 → 有界候选 | 边界、时间、来源、超长处理 |
| MemoryState | 快照 → 显式记录与依赖 | 统一计账、版本与可重建来源 |
| AgentManager | 可见状态 → 来源请求或联合计划 | 同一基座、结构化输出 |
| PlanValidator | 计划＋旧状态 → 合法暂存计划 | 引用、依赖、预算、有效性约束 |
| D2LBackend | 有界编译文本 → 内容因子 | 冻结编译、复用、原生组合 |
| SnapshotRuntime | 暂存快照 → 原子安装 | hook、KV、回退与暂存回收 |
| Evaluator | 冻结快照/环境 → 指标 | 问题隔离、机制分支、真实 rollout |

推荐里程碑：

| 阶段 | 应交付的东西 | 进入下一步的条件 |
| --- | --- | --- |
| M0 | schema、预算校验、人工计划驱动的状态转移 | 接纳、跳过、纠正、全局满、失败回退均可追溯 |
| M1 | 真实 D2L 多块编译与安装 | shared/scale/shape 正确；重置、复用和全量重建一致 |
| M2 | 同一 Agent 输出计划 | 能在预算内完成上述情形，报告真实管理失败率 |

| M5 | 真实交互任务与成本曲线 | 任务成功率和总成本能支撑完整 Agent 主张 |

M0/M1 需要有意义的状态测试：全局编译失败时不丢唯一来源、纠正失败时不恢复错误块、重复提交不重复叠加、没有悬空引用、管理模式不读到任务适配器、任务 KV 不跨参数版本复用。

| --- | --- | --- |
| D2L | 冻结路径生成与多块参数组合 | 有限容量下联合巩固/替换是否提升任务 |
| Memory-R1 / Uni-Mem 类管理器 | Agent 记忆动作及策略优化 | 同一冻结 Agent 的联合决策价值，而非记忆动作本身 |
| RPMem / DPPM | 跨会话参数巩固、双路径更新 | 显式有界来源＋可替换局部池上的耦合机制 |
| TrustMem / MemDream | 转换验证、自探针和修复 | 本方案不以额外验证器作为主要贡献 |
| WISE / MEMOIR | 参数组织、选择性激活及编辑干扰控制 | 不能把拆块或选择性更新本身称为首次提出 |

具体方法差异和最新文献仍需正式新颖性核查。本文没有足够证据声称已有方法无法完成同样的联合管理。

可用于论文的暂定动机：

> 在有界增量参数记忆中，局部块的退出同时决定容量释放与后续任务可能失去的证据。我们研究一种由现有 Agent 管理的维护流程，根据当前目标与已发生历史估计事实的后续用途，将选择性事实巩固与局部接纳、替换联合决策。在冻结编译器与显式来源预算下，以后续任务质量和总成本检验这一耦合的价值，并通过事实保持、更新正确性和行动变化分析收益或失败的来源。

## 14. 最值得继续讨论的优化

全局以事实为主要内容、以帮助解决后续真实问题为目标已经明确；其余建议按影响排序，避免首版同时增加很多模块。

| 优先级 | 讨论点 | 当前决定/建议 | 主要代价/改变 |
| --- | --- | --- | --- |
| 1 | 全局记忆跨多大范围 | 先同一任务/项目跨阶段 | 跨用户会改变作用域隔离、可访问来源与评测单位 |
| 2 | 全局主要保存什么 | **已明确：选择有后续任务价值的事实**；持续约束、关键关系、具体事件结果 | 用途只能由当前前缀估计；保护必要限定，避免追求条目数量 |
| 3 | 巩固何时发生 | 普通更新与局部替换联合；纠正和强约束即时处理 | 全量每步重建开销高；只等淘汰又可能更新过晚 |
| 4 | 是否每次验证可读性 | 首版离线系统测；必要时只对重要写入做有预算探针 | 在线探针也会漏测，并增加调用/读取成本 |
| 5 | 两层如何分配 rank | 先固定 4＋4，再在总宽度不变下测 2＋6、6＋2 | 动态分配需要新增决策，暂不放首版 |
| 6 | 是否每次读取所有局部块 | 首版全部激活；确认干扰后再比较任务相关选择 | 选择器可能漏掉跨块证据 |
| 7 | 何时考虑训练 | 先定位同一 Agent 的系统性决策失败 | 若瓶颈在 D2L 可读性，训练淘汰策略未必有用 |

接下来优先明确要服务的真实问题及其失败方式，再细化事实粒度与全局满时的取舍。当前建议是：以可独立理解、能支持后续判断的事实关系为保留单元；全局满时先去重和压缩冗余，再按预计任务价值选择遗忘，避免用含糊概括掩盖有用事实的丢失。

关键验证链是：**旧原文退出后，有用事实能否被正确读出 → 能否结合新观察支持正确行动 → 能否改善任务结果或减少总成本。** 新局部槽位也要体现对任务的新增收益。本次内容与目标选择不自动确认跨任务或跨用户范围，“全局”的作用范围仍按第 2 节的协议分别处理。
